## Low severity

### 1. Best-effort photo destroys run before the response, against the write deadline

**Files**: `internal/handler/recipe_handler.go:163,193`,
`internal/handler/account_handler.go:317-321`,
`internal/handler/recipe_images.go:69-98`,
`internal/cloudinary/client.go:37`, `lifecycle.go:40`

Recipe update and delete destroy an orphaned photo after commit, then
write the response. `DELETE /me` (`CROC-030`) does the same for every
orphaned photo of the user's drafts, one Cloudinary call at a time. Each
call has the client's 20s timeout and runs under `context.WithoutCancel`.
The server's `WriteTimeout` is 15s. A single slow destroy outlasts it, so
a committed delete can reach the client as a dropped connection.

Nothing is lost: the destroy is best-effort by design, and a retry gets
404 (recipe) or 401 (account, which signs that device out). The user
sees a failure for something that worked, though, and `DELETE /me`
multiplies the exposure by the number of photos.

`CROC-068` covers the same budget problem for photo *uploads* and does
not mention destroys. The fix belongs in the same place: write the
response first and destroy afterwards (a bounded background call, or
after the handler has flushed), so the deadline can't decide whether a
committed change reports success.

### 2. The token tables' `user_id` indexes are partial, so the user-delete cascade can't use them

**Files**: `db/migrations/000001_init.up.sql:46-47,60-61`,
`internal/repository/schema_test.go:16-56`

`email_verification_tokens.user_id` and `password_reset_tokens.user_id`
have only partial unique indexes (active tokens only). `CROC-030` made
deleting a user a real path, and its `ON DELETE CASCADE` deletes *every*
token row for the user, used and expired ones included. That delete
can't use a partial index, so it scans the table. The tables are small
today (the daily sweep prunes them), so this costs nothing yet. It is
the one FK without a usable index, and nothing would catch it growing.

`TestSchemaFKColumnsAreIndexed` doesn't list either column. Its query
would also pass a partial index (it never checks `pg_index.indpred`).
`CROC-071` already plans to derive that list from `pg_constraint`, which
would pick up both columns and then pass on the partial indexes. So
`CROC-071` should also reject partial indexes, and add plain `user_id`
indexes to the two tables.

### 3. Test plumbing is copied per file instead of shared

**Files**: `internal/handler/*_test.go` (39 `do…` request helpers),
`internal/handler/account_handler_test.go:186,523`,
`internal/repository/recipe_test.go:16,28,1070,1079`

- **Handler tests:** 39 hand-written `do…` helpers each rebuild the
  same request: JSON-encode the body, set `Content-Type`, set
  `Authorization`, serve. Body encoding is written out 19 times.
  `CROC-051` added `jsonRequestBody` to `helpers_test.go`, but only the
  `/me` tests use it. Every new endpoint copies another helper.
- **Two near-identical closures:** `account_handler_test.go` has two
  `rejectedBeforeLock` closures (delete and change-password) that differ
  only in mock type and return arguments.
- **Repository tests:** shared fixtures live in whichever entity's test
  file needed them first. `insertTestUser` and `insertTestRecipeRow` are
  in `recipe_test.go` and used by 9 and 6 files. `waitForLockWait` and
  `releaseOnce` are in `recipe_test.go` too, used by 4 files including
  `account_test.go` and `user_test.go`. A new test author has to know
  where to look, or writes a duplicate.

One generic `doJSON(r, method, path, body, authHeader)` in
`helpers_test.go`, and a `fixtures_test.go` holding the cross-entity repo
fixtures and lock helpers, would collapse most of it. It's a mechanical
move. The risk is only in getting it wrong, and the existing tests
check that.
