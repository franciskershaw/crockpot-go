## High severity

### 1. `PostgresEmailVerificationTokenRepository` doesn't honor an active transaction

**File**: `internal/repository/email_verification_token.go:15-21`

Every other repository (`user.go`, `refresh_token.go`,
`password_reset_token.go`, `item_category.go`, `unit.go`) stores `db
sqlc.DBTX` and calls `queriesFor(ctx, r.db)` per method — `tx.go:16-21`'s
helper that picks up the active `pgx.Tx` from context if
`PostgresTransactor.WithinTx` set one, falling back to the pool
otherwise. `PostgresEmailVerificationTokenRepository` instead stores `q
*sqlc.Queries` constructed once in its constructor, bound permanently to
the raw pool — it can never see a transaction, regardless of what `ctx`
it's called with.

**Why it matters**: this is a silent atomicity trap, not (yet) a live
bug. Checked every current call site (`auth_handler.go`, all
`emailVerificationTokenRepo.*` calls at lines 326/334/343/350/384/401/417)
— none currently run inside a `transactor.WithinTx(...)` block, so
today's behavior is correct by accident. But `ResetPassword`
(`auth_handler.go:685`) already wraps a near-identical shape of
multi-repo write (mark-token-used + user update + refresh-token
revocation) in exactly one `WithinTx` block, and `Register`'s "delete the
old active token, then create a new one" (`auth_handler.go:334,343`) is
the same kind of should-probably-be-atomic pair. The moment a future
ticket wraps `emailVerificationTokenRepo` calls in `WithinTx` — a
natural, likely change — the compiler won't catch it, the handler-mock
tests won't catch it (they mock the repo entirely), and it will silently
commit outside the transaction, immune to a later rollback.

**Fix**: change the struct to `db sqlc.DBTX` and every method to
`queriesFor(ctx, r.db)`, matching `password_reset_token.go`'s existing
pattern exactly. Mechanical, no behavior change today; closes the trap
before it's triggered.

**Ticket**: `CROC-031`.

## Medium severity

### 2. Missing indexes on FK columns across the schema

**File**: `db/migrations/000001_init.up.sql`

Postgres does not auto-index a foreign-key column (only the referenced
side, via its primary key). Ten FK columns in the base schema aren't the
leading column of any index, PK, or unique constraint:

| Column | Line |
| --- | --- |
| `items.category_id` | 85 |
| `item_allowed_units.unit_id` (2nd col of composite PK only) | 94 |
| `recipes.created_by_id` | 118 |
| `recipe_ingredients.item_id` | 128 |
| `recipe_ingredients.unit_id` | 129 |
| `recipe_favourites.recipe_id` (2nd col of composite PK only) | 146 |
| `recipe_menu_entries.recipe_id` | 162 |
| `menu_history_entries.recipe_id` | 172 |
| `shopping_list_items.item_id` | 193 |
| `shopping_list_items.unit_id` | 194 |

(Checked and *not* gaps: `recipe_ingredients.recipe_id` is the leading
column of `UNIQUE (recipe_id, item_id)`; `recipe_categories_recipes`,
`recipe_favourites.user_id`, `recipe_menus.user_id`,
`shopping_lists.user_id` are all covered by their own PK/unique
constraints or an existing explicit index.)

**Why it matters**: most of these tables (`recipes`, `recipe_ingredients`,
`recipe_menus`, `shopping_lists`, `recipe_favourites`) have no handler
built yet (Epic 4-6), so this is forward-looking, not an active
performance problem. `items.category_id` and `item_allowed_units.unit_id`
are the two that become live at `CROC-012`. Cheap to fix now, in one
migration, before any of these tables carry real rows — an index added
later against a populated table is a heavier operation.

**Ticket**: `CROC-032`.

### 3. No periodic cleanup of stale/expired token rows

**Files**: `lifecycle.go:1-53` (dead code), `db/migrations/000001_init.up.sql:21-62`
(`refresh_tokens`, `email_verification_tokens`, `password_reset_tokens`)

`lifecycle.go` has ~15 lines of commented-out code — a `runTokenSweeper`
goroutine and a `tokenSweepRepository` interface expecting a
`DeleteAllStaleFamilies(ctx) error` method. That method doesn't exist
anywhere in the codebase; the real, built method is
`DeleteStaleFamiliesForUser(ctx, userID)` (`refresh_token.go:45`),
called per-user only on that user's next login (`auth_handler.go:143`).
The commented code is stale against the current interfaces, not just
unused.

**Why it matters**: right now, all three token tables only ever shrink
opportunistically — a user who registers and never returns, or requests
a password reset and never uses it, leaves rows in `refresh_tokens`,
`email_verification_tokens`, or `password_reset_tokens` forever. No
TTL/cron/`pg_cron` job exists. Unbounded but slow growth — not urgent
before real traffic, but worth a real decision (build the sweep, or
explicitly decide it's not needed yet and delete the dead code with a
one-line reason) rather than leaving commented-out code implying "someday."

**Ticket**: `CROC-033`.

### 4. No request body-size limit anywhere

**Files**: `internal/middleware/` (no such file exists), `main.go` (no
`http.MaxBytesReader` or equivalent applied)

`CLAUDE.md`'s own folder-layout doc (written at `CROC-001`, mirroring
`packing-list-go`) states `middleware/` covers "Auth, CORS, rate
limiting, body-size limits, error logging." Auth, CORS, and rate
limiting all exist (`auth.go`, `cors.go`, `rate_limit.go`); body-size
limiting doesn't — checked every file in `internal/middleware/` and every
`server.Use(...)` call in `main.go`.

**Why it matters**: every JSON-binding endpoint (`register`, `login`,
`item-categories`/`units` create/update, and everything Epic 4-6 will
add) has no cap on request body size. `c.ShouldBindJSON` buffers the
full body before validation runs — an oversized request forces full
buffering per request, a cheap resource-exhaustion vector, and a
doc/reality mismatch on top of the security gap.

**Ticket**: `CROC-034`.

## Low severity

### 5. Duplicated email-sending logic

**File**: `internal/email/resend.go:60-100` (`SendConfirmationCode`) and
`:102-142` (`SendPasswordResetLink`)

The two methods are ~35 lines each of near-identical
boilerplate — render HTML+text templates, marshal a
`resendEmailRequest`, build the HTTP request, send it, check the status
range, read an error body on failure — differing only in which
templates/data/subject are used.

**Why it matters**: a third email type (this product will likely add
more — e.g. a welcome email, a recipe-approval notification) means a
third copy-paste. A shared `send(ctx, toEmail, subject, html, text
string) error` helper collapses both call sites to ~10 lines each.

**Ticket**: `CROC-035`.

### 6. Rate-limit error bodies don't follow the established error-shape convention

**File**: `internal/middleware/rate_limit.go:28,31`

`master-spec.md`'s "API error response shape" decision (locked at
`CROC-005`): failures return `{"error": "snake_case_code"}`. Every
handler-level error follows this (`invalid_request`, `server_error`,
`name_taken`, ...). `rate_limit.go` doesn't: `{"error": "rate limit
exceeded"}` and `{"error": "internal server error"}` are sentence-style,
not snake_case codes.

**Why it matters**: this is the one place in the API that breaks its own
documented contract — `crockpot-react` (or any client) that switches on
error codes has no consistent way to detect a rate-limit response
programmatically. Trivial fix: `rate_limit_exceeded` and `server_error`
(reusing the code every other 500 in this codebase already uses).

**Ticket**: `CROC-036` (bundled — same "bring existing code into line with
an established convention" theme as findings 7 and 8).

### 7. `db.go` bypasses the app's structured logger

**File**: `db/db.go:48,71,80`

`main.go:37` sets `slog.SetDefault(slog.New(slog.NewTextHandler(os.Stdout,
nil)))` as the app's logger, explicitly to match Gin's default writer so
output interleaves in order — and the rest of the app uses it
consistently (`c.Error(...)` surfaced by Gin's own logger, `slog.Info("shutting
down")` in `main.go`). `db.go`'s three log lines (`"Database connection
established"`, migrator-close failures, `"Migrations completed
successfully"`) use raw `fmt.Println`/`fmt.Printf` instead, bypassing
`slog` entirely.

**Why it matters**: minor today (single-process, stdout either way), but
inconsistent — unstructured output can't be filtered/parsed the way the
rest of the app's `slog` output can once log aggregation matters, and
it's the one place the "structured logging rather than ad-hoc prints"
principle isn't followed.

**Ticket**: `CROC-036` (bundled).

`CROC-010`'s handoff doc (decision 6) explicitly flagged this: *"Not

handoff doc.

**Ticket**: `CROC-036` (bundled).

### 9. Two Postgres driver libraries for one job

**Files**: `db/db.go:13,15`, `go.mod:13`

The app uses `pgx/v5` exclusively for every query and the connection
pool (`pgxpool`). `db.go` also blank-imports `github.com/lib/pq` purely
so `golang-migrate`'s `database/postgres` driver (a `database/sql`-based
driver) has something to register against for running migrations.
`golang-migrate` ships a native `database/pgx/v5` driver
(`github.com/golang-migrate/migrate/v4/database/pgx/v5`) that would let
migrations run through the exact same `pgx` stack the rest of the app
uses.

**Why it matters**: not a bug — just an unnecessary second Postgres
client library in the dependency tree (and the `database/sql` code path
it drags in) for a job `pgx` can already do. Small, mechanical swap.

**Ticket**: `CROC-037`.
