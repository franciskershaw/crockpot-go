## Findings

### 1. Refresh cookie is `SameSite=None` in production, against the recorded domain decision — low

**File**: `internal/handler/auth_handler.go:112-119` (`setRefreshCookie`)

Production sets `SameSite=None`. `crockpot-react`'s spec ("Domain
layout") chose `crockpot.app` + `api.crockpot.app` specifically so the
cookie stays same-site (`Lax`/`Strict`). The frontend calls with
`credentials: "include"` (`crockpot-react` `src/lib/http/client.ts:49,91`),
and a same-site request carries a `Lax` cookie, so `None` buys nothing.
What it costs: any other site can make the browser send the cookie on a
cross-site `POST`. `POST /auth/logout` then revokes the user's session
(forced logout), and a cross-site `POST /auth/refresh` rotates the family
behind the real tab's back. Responses aren't readable cross-site (CORS
allows one origin), so no token leaks.

**Fix**: `Lax` in every environment. Revisit only if the frontend ever
moves to a different registrable domain.

### 2. JWT secret strength and reuse aren't enforced — low

**Files**: `config/config.go` (`validate`), `internal/auth/jwt.go`

The three secrets are only required to be non-empty. Tokens are HS256, so
anyone holding one valid access token can brute-force a weak secret
offline and then mint `role: ADMIN`; `RequireRole` trusts the claim
without a database lookup. `packing-list-go` issues tokens with the same
claim shape (`email`/`userID`/`role`), so reusing its secrets here would
make its tokens valid in this API. Dev secrets are fine (44 chars each,
all distinct, checked without printing).

**Fix**: refuse to start unless each secret is at least 32 bytes and all
three differ. Add to `CROC-077`'s runbook: generate fresh secrets
(`openssl rand -base64 32`), never reuse another app's.

### 3. Browse filters accept an unbounded number of ids — low

**File**: `internal/handler/recipe_requests.go` (`parseUUIDQuery`)

`categoryId` and `ingredientId` are capped only by URL length (Go's 1 MB
header limit), so one request can pass tens of thousands of ids into the
ranking query. The 14s request deadline (`CROC-066`) and the 120/min
global rate limit bound the damage, but a single request can still burn
14s of database time.

**Fix**: cap each list (e.g. 50, comfortably above what the filter UI can
produce) with `400 invalid_request`, matching the body-side caps on
recipe ingredients (50) and categories.

### 4. Request logs contain the OAuth `code` and `state` — informational

**File**: `main.go:111` (`gin.Default()`)

Gin's default logger writes every request's full URL, so each Google
callback logs `?code=…&state=…`. The code is single-use and exchanged
within the same request, so a log reader can't replay it. Noted so the
deploy's log retention doesn't treat these lines as secret-free.

**Fix (optional)**: a logger config that drops the query string for
`/auth/google/callback`.

### 5. Google sign-in asks for offline access it never uses — informational

**File**: `internal/auth/google.go:83` (`oauth2.AccessTypeOffline`)

Google issues a refresh token that's discarded; the app only needs the
ID token at sign-in. Requesting it widens what a leaked exchange would
grant and can add "offline access" to the consent screen.

**Fix**: drop `AccessTypeOffline` (online access is the default).

## Checked clean

- **Route guards** (`main.go`): every write route sits behind
  `AuthMiddleware`; every reference-data write and `PATCH
  /recipes/:id/approve` adds `RequireRole("ADMIN")`. Auth routes share a
  10/min per-IP limit; password-checking `/me` routes add it too.
- **JWT handling** (`internal/auth/jwt.go`): HS256 pinned
  (`WithValidMethods`), expiry enforced, access/refresh/OAuth-state
  signed with separate secrets; an empty `userID` claim is rejected
  (`handler/context.go:11`), so a mixed-up token type gets 401.
- **Google OAuth** (`internal/auth/google.go`, `auth_handler.go:155-245`):
  OIDC discovery, ID token verified against the client id,
  `email_verified` required, signed state with a 10-minute expiry plus a
  double-submit `HttpOnly` cookie. A Google sign-in can't attach to a
  password account (`ErrEmailRegisteredWithPassword`).
- **Codes and tokens** (`internal/auth/token.go`): `crypto/rand`,
  stored as SHA-256 hashes. Confirmation codes: 5 attempts per code,
  claimed atomically (`CROC-069`), one resend per minute per account, so
  guessing is capped near 5 per minute per account whatever the IP count.
  Reset tokens: 256-bit, single-use (atomic claim), revoke every session.
- **Refresh rotation** (`auth_handler.go` `RefreshToken`): family lookup
  scoped to the token's subject, atomic rotate with a grace window, reuse
  revokes the family, user looked up before rotating. Logout revokes the
  family and always clears the cookie.
- **Per-user scoping**: every id-keyed `UPDATE`/`DELETE` in
  `internal/sqlc/queries/` carries `user_id` or the caller's list/menu
  id. The two that key on `id` alone take ids from caller-scoped lookups
  (`IncrementShoppingListItemQuantity` via `FindShoppingListItemForMerge`,
  `repository/shopping_list.go:71-93`; `RestockResetBoughtRows` via
  `regular_items.user_id` + the caller's list).
- **Recipe permissions**: `approved` is set from the caller's role, never
  the body (`recipe_handler.go:82`); update/delete/favourite pass the
  caller to the repository's write-lock check; hidden recipes 404 like
  missing ones; `approved=false` listing still goes through
  `recipe_visible_to`.
- **SQL injection**: every query is sqlc-generated and parameterised; no
  SQL built with `Sprintf` in `internal/repository`. The unescaped `%`/`_`
  in recipe search was already judged cosmetic
  (`docs/findings/2026-10-02-tech-debt.md`).
- **Uploads**: size checked before and during reading, type sniffed from
  content against an allow-list, public id generated server-side,
  destroys confined to configured folders (`config.validateUploadFolder`,
  `ImageScope`). The 6 MiB body cap bounds multipart parsing.
- **Errors and emails**: clients only ever see the generic
  `server_error`; details go to the log. Email HTML uses `html/template`
  and interpolates only the code and server-built URLs.
- **CORS**: one exact origin, credentials only for it, `Vary: Origin`.
- **Passwords**: bcrypt default cost, 8–72 bytes enforced.
