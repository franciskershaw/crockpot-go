## Medium severity

### 1. Shopping-list unit merging finds its base units by display name

**File**: `internal/sqlc/queries/shopping_list.sql:31-32` (`AggregateMenuIngredients`)

The aggregate resolves the mass/volume base units with
`(SELECT id FROM units WHERE name = 'grams')` and
`... WHERE name = 'milliliters'`. Unit names are admin-editable
(`PATCH /units/:id` → `UpdateUnit`, `units.sql`), and nothing protects
these two rows.

**Failure scenario**: an admin renames `grams` → `gram`. The names are
already inconsistent (`grams`, `kilogram`, `litres`, `cup`, `pint`;
`000011_shopping_list_unit_dimensions.up.sql`), so this is the kind of
tidy-up someone would actually do. `grams_id` becomes NULL, so
`COALESCE(base_unit_id, unit_id)` falls back to each row's own unit, but
the quantity is still multiplied by `base_factor`. A recipe needing 2 kg
of flour then appears on every holder's list as **2000 kg**. This
happens silently for every user on their next menu write, with no error
anywhere. Deleting the `grams` row would have the same effect.

**Fix**: key the lookup on the data the migration already set:
`WHERE dimension = 'mass' AND base_factor = 1` (and the same for
volume). Back it with a partial unique index (one `base_factor = 1` unit
per non-count dimension) so the lookup can't become ambiguous. Add a
real-DB test that renames `grams` and asserts a kg ingredient still
aggregates into grams.

**Ticket**: `CROC-063`.

## Low severity

### 2. No upper bound on ingredient/shopping-list quantities, so a NUMERIC overflow returns 500 instead of 400

**Files**: `internal/handler/recipe_requests.go:210`,
`internal/handler/shopping_list_requests.go:36,60`;
`internal/sqlc/queries/shopping_list.sql:55,119`; columns
`NUMERIC(10, 2)` (`000001_init.up.sql:130,195`)

Validation only rejects `<= 0`. The columns cap at 99,999,999.99, and
`AggregateMenuIngredients` casts its scaled sum back to
`numeric(10, 2)`. Overflow is SQLSTATE `22003`, which `pgConstraintError`
doesn't map (it matches constraint names only), so each of these returns
a generic `500 server_error`:
- a recipe or manual add with a quantity ≥ 1e8;
- a valid recipe quantity that overflows only after scaling. For example,
  50,000 kg of an item becomes 5e7 g after `base_factor` 1000, then × 2
  at serves 4/2 = 1e8 g. The menu upsert 500s, as does any later recipe
  edit by an admin, because `Update` regenerates every holder's list
  (CROC-062);
- repeated manual adds that push `quantity + delta` past the cap.

It's also true at the low end: a quantity between 0 and 0.005 passes
`> 0`, then rounds to `0.00` on insert.

No client-side cap exists either (`crockpot-react` has no quantity
`max`), so the backend is the only guard.

**Fix**: a shared `validateQuantity` in `validation.go` with a
deliberately chosen ceiling (well under 1e8, e.g. 100,000), plus a floor
of ≥ 0.01, used by all three call sites. Map `22003` from the aggregate
and increment paths to a domain error (→ 400 `quantity_too_large`)
rather than a 500.

**Ticket**: `CROC-064`.

### 3. Shopping-list error codes drift from the rest of the API for the same failures

**Files**: `internal/handler/shopping_list_handler.go:63,65,67` vs
`recipe_handler.go:322,324,328` and `item_handler.go:159`

The same sentinel produces different codes depending on the endpoint.
`models.ErrIngredientUnitNotAllowed` → `unit_not_allowed_for_item`
(recipes) vs `unit_not_allowed` (shopping list). Bad item/unit FKs →
`invalid_item_id` / `invalid_unit_id` (recipes, items) vs
`invalid_item` / `invalid_unit` (shopping list). Three handlers use one
spelling and one handler uses the other.

**Why it matters**: the error-code contract (`CROC-005`/`041`) exists so
clients can switch on codes. Checked `crockpot-react/src`: no non-test
code branches on any of the six strings today, so aligning them now
breaks no caller. That won't stay true once a shopping-list error UI is
built.

**Fix**: rename the shopping-list three to the recipe spellings; update
`shopping_list_handler_test.go` and `requests/shopping-list.http`.

**Ticket**: `CROC-064` (same input-validation surface as finding 2).

### 4. Recipe visibility rule and list filters hand-copied across queries

**Files**: `internal/sqlc/queries/recipes.sql:85` (`ListRecipes`),
`:159` (`CountRecipes`), `:196` (`GetRecipeForReader`);
`internal/sqlc/queries/favourites.sql:8` (`RecipeVisibleToCaller`)

The visibility predicate (approved, or caller is admin, or caller is the
creator) is written out in four queries. It is the authorization
boundary for unapproved recipes, and `RecipeVisibleToCaller` already
spells it differently (no `caller_id IS NOT NULL` guard; it relies on a
non-null param). Separately, `ListRecipes` and `CountRecipes` repeat the
whole filter clause, and it has already diverged in form: `ListRecipes`
gates the include/ingredient match on a `has_score_signal` param, while
`CountRecipes` recomputes the same condition from the array
cardinalities. These are equivalent today only because
`recipe.go:List` derives `hasScoreSignal` the same way.

**Why it matters**: the next visibility change (e.g. a "rejected" state
from recipe moderation, which `CROC-062` makes more likely) must land
four times. A missed copy either leaks a hidden recipe (detail/favourite
/menu) or makes `total`/`totalPages` disagree with the rows returned.

**Fix**: move the predicate into one SQL function in a migration, e.g.
`recipe_visible_to(r recipes, caller uuid, is_admin bool) RETURNS bool`,
and call it from all four queries. For List/Count, a real-DB test
asserting `total` equals the row count across each filter combination
is cheaper than merging the queries (sqlc can't share fragments).
Decide at grill whether the function is worth it versus the test alone.

**Ticket**: `CROC-065`.

### 6. DB pool has default sizing and no statement timeout

**File**: `db/db.go:31-35`

Only `DefaultQueryExecMode` is set. pgxpool defaults to
`max(4, NumCPU)` connections, which is 4 on a 1-vCPU droplet. Nothing
bounds query duration. `http.Server.WriteTimeout` (15s) does not cancel
the handler's request context, so a slow query keeps holding its
connection after the client's write has already failed. That is exactly
the `/items` 26s incident shape in `CROC-045`, whose "DB-pool contention?"
question was left unconfirmed. Recipe `Update`/`Delete` (CROC-058/062)
now regenerate every holder's list inside one tx, so a single request's
connection hold time grows with how many menus hold the recipe.

**Fix**: set `MaxConns` explicitly (sized against Neon's pooler limit,
not CPU count). Add a server-side `statement_timeout` via the pool's
`RuntimeParams`, a little under `WriteTimeout`, so a runaway query frees
its connection. Exercise both through the real client, per the global
"limits, thresholds, config" rule.

**Ticket**: `CROC-066`. *Time-coupled: do this alongside the (not yet
ticketed) deploy pipeline, where the droplet's real CPU count and Neon
plan are known.*

### 7. Token sweeper never runs if the process restarts more often than daily

**File**: `lifecycle.go:57`

`runTokenSweeper` waits a full `tokenSweepInterval` (24h) before its first
sweep. Merge cadence over the last fortnight shows several days with 2–3
merges, so once each merge redeploys, stale token rows can go
indefinitely without being swept.

**Fix**: sweep once at startup, before entering the ticker loop. Extend
the existing lifecycle test to assert a sweep happens without a tick.

**Ticket**: `CROC-066` (same "behaves correctly once actually deployed"
theme; same time-coupling).
