## Medium severity

### 1. `internal/middleware/auth.go` and `role.go` break the project's own API error-shape contract

**Files**: `internal/middleware/auth.go:15,21,28`, `internal/middleware/role.go:20`

`master-spec.md`'s "API error response shape" decision (locked at
`CROC-005`, reaffirmed at `CROC-041`): every JSON-responding endpoint's
failures return `{"error": "snake_case_code"}`. `CROC-041` retrofitted
this across the entire `handler` package (`auth_handler.go` included) and
`middleware/rate_limit.go`. `internal/middleware/auth.go` — a different
package, evidently missed by that retrofit — still returns sentence-style
bodies: `{"error": "missing authorization header"}`,
`{"error": "invalid authorization header"}`, `{"error": "invalid
token"}`. `role.go`'s `{"error": "forbidden"}` happens to already be
snake_case-compliant (single word) but is a literal duplicate of
`handler/errors.go`'s own `forbidden()` helper's code, not sharing it
(a different package, so it can't call it directly — worth a shared
constant or comment noting they must stay in sync).

**Why it matters**: `AuthMiddleware` runs in front of every authenticated
endpoint in the API — this is one of the highest-traffic error paths in
the whole service, not an edge case. A client switching on error codes
(the entire reason the convention exists) gets an unparseable string for
every expired/missing/malformed token, exactly the failure mode `CROC-041`
was filed to eliminate. Not caught by `internal/middleware/auth_test.go`,
which only asserts the status code (`http.StatusUnauthorized`), never the
response body — confirmed by reading the test file, this isn't a gap the
test suite already covers and tolerates.

**Fix**: `missing_authorization_header`, `invalid_authorization_header`,
`invalid_token` (or collapse all three to the existing `unauthorized`
code the rest of the app already uses for 401s, if per-cause detail isn't
needed client-side — a call for whoever picks this up, not decided here).
Mechanical either way, no behavior change beyond the response body text.

**Ticket**: `CROC-046`.

## Low severity

### 2. Recipe ingredient/category-link write loops duplicated between `Create` and `Update`

**File**: `internal/repository/recipe.go:335-367` (`Create`) and
`:430-462` (`Update`)

Both methods contain the same ~30-line pair of loops, unchanged since
`CROC-016` added `Update`/`Delete` without extracting a helper from the
`CROC-014`-era `Create`: one loop builds a `sqlc.CreateRecipeIngredientParams`
per ingredient (numeric-quantity conversion, optional unit, position
index) and calls `CreateRecipeIngredient`; the other calls
`CreateRecipeCategoryLink` per category ID. Both loops map the same
constraint error through `pgConstraintError(err, recipeConstraintErrors)`
identically in both places. (`checkAllowedUnits`, doing the same job for
a different piece of the same two methods, was already extracted at
`CROC-016` — this is the one piece of that ticket's shared logic that
wasn't.)

**Why it matters**: purely a maintenance-cost duplication, not a live bug
— both copies are currently correct and identical. But it's exactly the
kind of unreconciled duplication a schema or validation change to
ingredient/category writes would now need to land twice, silently
drifting if only one copy gets updated.

**Fix**: two small helpers —
`insertRecipeIngredients(ctx, q, recipeID pgtype.UUID, ingredients []models.Ingredient) error`
and `linkRecipeCategories(ctx, q, recipeID pgtype.UUID, categoryIDs []uuid.UUID) error`
— called from both `Create` and `Update`. Mechanical, no behavior change;
existing `recipe_test.go`/`recipe_handler_test.go` coverage should stay
green unmodified.

**Ticket**: `CROC-047`.

### 3. `serves` bounds check (1-50) duplicated three times instead of extracted

**Files**: `internal/handler/menu_requests.go:23,36`,
`internal/handler/recipe_requests.go:55`

`if req.Serves < 1 || req.Serves > 50 { badRequest(c, "invalid_serves") }`
appears verbatim in `parseUpsertMenuEntryRequest`,
`parseMenuEntryServesRequest`, and `parseCreateRecipeInput`.
`handler/validation.go` is this project's own established convention for
exactly this situation — `validateName`, `validateIconToken`,
`validateAbbreviation`, `validateCategoryID` each exist specifically
because a field-level check got used more than once. `serves` cleared
that same bar (3 call sites, 2 files) without getting the same
treatment.

**Why it matters**: low value on its own — the three copies are trivial
and currently in sync — but it's the one field-level validator that
didn't follow this codebase's own documented pattern for when to extract
one, and a future change to the bound (e.g. raising the cap) is now a
3-site find-and-replace instead of a 1-line change.

**Fix**: `validateServes(c *gin.Context, raw int) (int, bool)` in
`validation.go`, replacing all three inline checks. Mechanical.

**Ticket**: `CROC-047` (bundled with finding 2 — same DRY-cleanup theme,
no shared code between the two but both mechanical single-PR fixes).

### 4. `AddFavourite`'s check-then-write isn't wrapped in a transaction

**File**: `internal/repository/favourite.go:12-43`

`AddFavourite` checks `RecipeVisibleToCaller` then, if visible, calls
`AddFavourite` (the insert) — a check-then-write pair, same shape as
`Update`/`Delete` in `recipe.go` (`GetRecipeForWrite` then act) and
`ResetPassword`'s multi-repo write, both of which run inside
`WithinTx`. Every other multi-step recipe/item/menu write handler
(`recipe_handler.go:65,94,118`) wraps its repo call in
`h.transactor.WithinTx(...)`; `AddFavourite`
(`recipe_handler.go:206`) does not — it's the one write path on
`RecipeHandler` missing it.

**Why it matters**: same "not yet exploited" shape as the first pass's
finding 1. Checked why it's currently harmless: nothing in this codebase
ever flips `Recipe.Approved` from true back to false after creation (no
approve/reject-toggle endpoint exists — `approved` is set once at
creation and only ever read afterward, confirmed by grepping every
`Approved` write site), and `recipe_favourites.recipe_id` is `ON DELETE
CASCADE` (confirmed in `db/migrations/000001_init.up.sql:146`), so a
deleted recipe's favourite rows clean up automatically rather than
orphaning. The moment a future ticket adds recipe re-approval/rejection
(plausible — Epic on recipe moderation isn't ruled out), this becomes a
real race: visibility flips between the check and the insert, and
`ListFavouriteRecipes` (`internal/sqlc/favourites.sql.go`) has no
visibility filter of its own — it would silently surface a
currently-invisible recipe in a user's favourites list.

**Fix**: wrap `h.repo.AddFavourite(...)` in `h.transactor.WithinTx(...)`
in `recipe_handler.go`'s `AddFavourite`, matching the other three. No
schema or query change needed — `AddFavourite`'s repository method
already goes through `queriesFor(ctx, r.db)`, so it already honors an
active tx from context; only the handler-level wrap is missing.

**Ticket**: `CROC-048`.
