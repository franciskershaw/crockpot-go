## Medium severity

### 1. Photo saves can outlive the server's write deadline, so a committed recipe returns a network error

**Files**: `lifecycle.go:34-43` (`newHTTPServer`),
`internal/cloudinary/client.go:37`, `internal/handler/recipe_handler.go:60-165`,
`main.go:36-37,117-120`

The server timeouts predate `CROC-040` and were never re-checked against
it. `CROC-040`'s handoff does not mention `ReadTimeout` or `WriteTimeout`.
According to `net/http`'s docs, `ReadTimeout` (10s) covers reading the
*whole* request, body included. `WriteTimeout` (15s) runs from the end
of the request headers until the response is written. Neither one
cancels the handler. A photo save runs these steps one after another,
all inside that 15s:

1. read the body, up to 6 MiB (`recipeWriteBodyBytes`);
2. upload to Cloudinary. The client's own timeout is **20s**, longer
   than the whole write budget;
3. the transaction. For an update, it regenerates every holder's
   shopping list (`CROC-058`/`062`).

**Failure scenarios**:
- A FREE user on a phone saves a new recipe with a 4 MB photo. The upload
  takes 6s and Cloudinary takes 10s. The handler keeps going and commits
  the recipe, but the write deadline has already passed, so the client
  gets a dropped connection. The user retries, which creates a second
  recipe and a second upload. Each retry also counts towards the 5-recipe
  cap and the 20/hour photo limit.
- On an uplink slower than about 5 Mbps, a 6 MiB body cannot be read in
  10s. `ParseMultipartForm` then fails with an i/o timeout, which
  `parseRecipeWrite` maps to `400 invalid_request`. That code tells the
  client the request was malformed, not that the connection was slow.

Not reproduced in this pass. The scenarios are reasoned from the
documented `net/http` semantics and the code above. Reproduce them with
a throttled real request when the ticket is worked.

**Deploy-time half**: the planned nginx in front of the API buffers the
request body by default (`proxy_request_buffering on`). That would take
the body-read step off Go's clock. However, nginx's default
`client_max_body_size` is **1m**, so every photo save over 1 MB would
get nginx's own 413 before reaching the API, unless the server block
raises it to at least 6m. Nothing in the repo records this yet.

**Fix (decide at grill)**: give the two recipe-write routes their own
deadlines through `http.ResponseController`
(`SetReadDeadline`/`SetWriteDeadline`, available in Go 1.26). Bring the
Cloudinary timeout under whatever write budget is left at that point.
Map a body-read timeout to its own code rather than `invalid_request`.
Record `client_max_body_size` in the deploy notes. Whether the
duplicate-on-retry case also needs an idempotency key is a question for
the grill.

**Ticket**: `CROC-068`. *Half time-coupled: the nginx line belongs with
the (not yet numbered) deploy-pipeline ticket; the deadline/timeout
alignment does not.*

### 2. Email addresses are matched case-sensitively

**Files**: `db/migrations/000001_init.up.sql:8` (`email TEXT UNIQUE`),
`internal/sqlc/queries/users.sql:6-7` (`WHERE email = $1`),
`internal/handler/auth_handler.go` (`Register`, `Login`, `ConfirmEmail`,
`ResendConfirmation`, `ForgotPassword`), `internal/repository/user.go:24-55`
(`GetOrCreateUser`)

The code normalises email nowhere: no `ToLower`, `citext` or
`lower()` index. Searched `internal/`, `db/` and `cmd/` for all three,
and `docs/`, `LESSONS.md` and `CLAUDE.md` for any decision about it.
The question has never come up.

**Failure scenarios**:
- Someone registers as `Jane@Example.com`, for example because a phone
  keyboard auto-capitalised the first letter. Later they log in as
  `jane@example.com` and get `401 invalid_credentials`. Forgot-password
  for the lowercase form returns `email_not_found`.
- The same person can register `jane@example.com` as a second account,
  which splits their recipes, menu and shopping list across two users.
- A password account `Jane@Example.com` exists, and Google login arrives
  with `jane@example.com`. The unique constraint doesn't fire, so a
  separate Google account is created. The intended outcome is
  `email_registered_with_password`.

This is cheap to fix now: the migration source
(`../crockpotV3.User.json`, 42 users) has no mixed-case addresses and no
addresses that differ only by case (counted, not eyeballed). So a
normalising migration has nothing to merge.

**Fix**: normalise (`TrimSpace` + `ToLower`) once at the boundary: each
auth request's email, and `IDTokenClaims.Email` from Google. Back it
with a migration that lowercases existing rows and replaces the unique
constraint with a unique index on `lower(email)`, or `citext` (decide at
grill). Add a repo test: register in mixed case, then find by lowercase.
`cmd/migrate-data` should lowercase on load too.

**Ticket**: `CROC-069`.

## Low severity

### 3. The confirmation-code attempt cap can be raced

**Files**: `internal/handler/auth_handler.go:380-397` (`ConfirmEmail`),
`internal/sqlc/queries/email_verification_tokens.sql:10-14`

`ConfirmEmail` reads `token.Attempts` and compares it with
`maxConfirmationAttempts` (5). Only after that does it compare the hash.
`IncrementAttempts` is an unconditional `attempts = attempts + 1`. If N
wrong guesses arrive at once, all of them read `attempts < 5`, and all N
are checked against the code. That's the same check-then-write shape as
`CROC-031`/`048`. The cap is the only per-code brute-force guard on a
6-digit code (`auth/token.go:11`). The auth rate limit is per IP
(10/min), so requests spread across IPs each get a full burst. `CROC-005`'s
handoff never discusses concurrency.

**Fix**: claim the attempt atomically before comparing:
`UPDATE … SET attempts = attempts + 1 WHERE id = $1 AND attempts < $2
RETURNING attempts`. If no row comes back, respond `too_many_attempts`.
Add a real-DB test that fires concurrent wrong guesses and asserts at
most 5 were checked.

**Ticket**: `CROC-069` (same auth-identity surface as finding 2).

### 4. Admin reference-data PATCH/DELETE return 500 for a malformed `:id`

**Files**: `internal/handler/item_category_handler.go:101,119`,
`unit_handler.go:101,119`, `recipe_category_handler.go:77,93`,
`item_handler.go:116,135`

These 8 routes pass `c.Param("id")` straight to the repository. Its
`uuidParam` failure is wrapped as a plain error rather than a sentinel,
so it falls through to `internalError`, and the client gets
`500 server_error`. Every handler written since `CROC-015` calls
`parseID` first and returns `400 invalid_request`. These four handlers
predate that convention, and none of their tests sends a malformed id.

**Fix**: `parseID` at the top of each, plus one malformed-id test per
handler (table-driven if it fits the existing files).

**Ticket**: `CROC-070`.

### 5. Role checks are string literals repeated across handlers and routes

**Files**: `internal/handler/recipe_handler.go:80,124,177,214,258,282`,
`menu_handler.go:61`, `recipe_handler.go:17` (`"FREE"`),
`main.go:160,170,180,190`

`c.GetString("role") == "ADMIN"` appears 7 times, `RequireRole("ADMIN")`
4 times, and the tier map keys on `"FREE"`. The DB `CHECK` constraint
(`000001_init.up.sql:11`) is the only list of valid values. A typo in
any one of these compiles fine and silently denies admin, or uncaps a
FREE user. `context.go` already has `userIDFromCtx` and is the natural
home for a sibling.

**Fix**: role constants in `models`, plus a `callerIsAdmin(c)` helper in
`context.go`. Swap every call site. A pure refactor, so existing tests
should stay green unmodified.

**Ticket**: `CROC-070` (same handler-convention drift as finding 4).

### 6. Shared helpers living in, or bypassed by, the wrong file

**Files**:
- `internal/repository/recipe.go:612-645`: `checkAllowedUnits` is
  defined among the recipe code, but `shopping_list.go:51` and
  `regular.go:170` call it too. Each of those builds a one-element
  `[]models.Ingredient` just to fit its signature.
- `internal/repository/user.go:43,66`: inline
  `errors.As` + `pgErr.Code == "23505"` + constraint-name checks.
  `pgerror.go` already provides `pgErrorCode`/`pgConstraintError`, and
  every other repository uses them.
- `internal/auth/jwt.go:27` (`refreshTokenExpiry`) and
  `internal/handler/auth_handler.go:20` (`refreshTokenTTL`) both define
  the 7-day refresh lifetime. If someone edits one and not the other,
  the JWT `exp`, the DB `expires_at` and the cookie `Max-Age` disagree.

**Fix**: move `checkAllowedUnits` into its own file (e.g.
`allowed_units.go`). Switch `user.go` to the `pgerror.go` helpers with
`pgerrcode.UniqueViolation`. Export a single refresh TTL from `auth` and
use it in the handler.

**Ticket**: `CROC-071`.

### 7. The FK-index schema test only checks the FKs someone remembered to list

**File**: `internal/repository/schema_test.go:17-57`

`TestSchemaFKColumnsAreIndexed` iterates a hand-kept list of 18
`(table, column)` pairs (`CROC-038`'s LESSONS entry caught a handoff
assuming otherwise). Every FK not on the list is covered today by a
PK or unique index that leads with it. That's checked against every
`REFERENCES` in `db/migrations/`. But a future migration that adds a
FK and forgets both the index and the list entry passes this test.

**Fix**: build the list from `pg_constraint` (`contype = 'f'`, first
column of `conkey`) instead of by hand. Keep the same `indkey[0]`
assertion.

**Ticket**: `CROC-071` (same "guard against drift" theme).
